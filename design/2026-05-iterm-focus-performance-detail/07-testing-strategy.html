§7 · Testing Strategy

Traces to Overview · G1-G5 全部 Goal 各自的 happy / edge / error 用例 + §3 不变量 I-1~I-5 + §4 错误矩阵

测试金字塔的边界

  • unit ── 不接触 NSAppleScript / NSRunningApplication 真实 API；用 PyObjC mock。覆盖 决策链、状态机、错误传播、frozen 字段不变量。
  • integration ── 真实 PyObjC + 假 iTerm（一个最小 AppleScript 测试夹具，下文 §7.5 详述）。 覆盖 cache 编译、worker pool 序列化、handler 行为。
  • e2e ── 真实 iTerm + 真实 session（手动 + 一个 CI-skippable 自动化夹具）。 覆盖 G2 端到端 wall-time、用户感知延迟。

7.1 G1 ── 主线程 ≤ 5 ms 验证

ID路径等级输入预期
G1.H1 happy unit (benchmark) Mock NSRunningApplication.runningApplicationWithProcessIdentifier_ 返回 fake app； fake app.activate_ 返回 True；Mock QThreadPool.start 立即返回； view 带 jump_target.terminal_pid=12345, iterm_session_id="abc" focus(view) 返回 True 且 median elapsed < 2 ms over 100 iter （pytest-benchmark）
G1.E1 edge unit view jump_target=None；走 _iterm_host_pid 路径（mock psutil 返回 12345） focus 返回 True；elapsed 多 ~0.3 ms 但仍 < 5 ms p95
G1.E2 edge integration 真实 PyObjC + fake iTerm 夹具；首次 + 第二次调用 首次 (含 import) < 50 ms；第二次 warm < 2 ms
G1.X1 error unit Mock NSRunningApplication.activate_ 抛 objc.error focus 不抛、转 fallback；返回值与 fallback 一致

7.1.1 通过准则

  • tests/platform_/test_iterm2_fast_path_perf.py::test_warm_path_under_5ms ── pytest-benchmark median < 2 ms / p95 < 5 ms
  • 该测试 100 次连续运行，零 flake（CI tolerance ±20%）

7.2 G2 ── 端到端 wall-time ≤ 50 ms p95

ID路径等级输入预期
G2.H1 happy e2e 真实 iTerm 启动，4 个活跃 session；测试夹具点击其中一个 row，记录 mouse-up → WindowServer 触发"iTerm 在前"事件的差 p95 < 50 ms 在 100 次试验中
G2.E1 edge e2e 2 个并行 iTerm 实例（3.6.9 + 3.6.10）；点击属于第二个实例的 session 正确的 iTerm 实例前置（验证 host_pid 路由），p95 < 50 ms
G2.X1 error e2e iTerm 进程被 kill -STOP 模拟 hang；点击 row fast-path 返回 True 但 pane select 进入 backlog → 解 STOP 后队列清空，没崩

e2e 测试夹具 ── 选型

方案 A：基于 NSWorkspace.frontmostApplication 轮询（10 ms 间隔）。 方案 B：基于 NSWorkspaceDidActivateApplicationNotification。
采用 B：事件驱动，无轮询误差；唯一前置是 e2e fixture 启用 NSWorkspace.notificationCenter 监听。

e2e 默认在 CI 上 skip（需真实 iTerm + 真实 session）；本地开发用 pytest -m e2e 触发。CI Mac runner 若资源允许后续可启用。

7.3 G3 ── pane 精度不退化

ID路径等级输入预期
G3.H1 happy integration fake iTerm 夹具，3 个 session（id=A/B/C，对应 tty=tty1/tty2/tty3）；提交 task(session_id="B") id_handler 命中；fake iTerm 内部 selected_session == "B"
G3.H2 happy integration 同上但 task(session_id=None, tty="tty2") tty_handler 命中；selected_session == "B"
G3.E1 edge integration task(session_id="X-stale", tty="tty2") —— id 已不存在，tty 有效 id_handler miss → 转 tty_handler → ok；cache counter 未递增（miss 不算失败）
G3.E2 edge integration task(session_id="X-stale", tty="tty-stale") —— 双双失效 两 handler 都 miss；log.info "pane select miss"；fast-path 仍已让 host 前置
G3.X1 error unit 构造 task(session_id=None, tty=None) raise ValueError（§2 不变量 assert）
G3.X2 error integration fake iTerm 模拟 -1743 权限错误返回 note_failure → counter++；连续 3 次后 invalidate；log.error 一次

7.4 G4 ── PyObjC 不可用降级

ID路径等级输入预期
G4.H1 happy unit Monkeypatch sys.modules['AppKit'] = MagicMock 抛 ImportError； 调用 focus(view) _HAS_PYOBJC = False；不调用任何 PyObjC API； 完整走 _legacy_focus 路径（subprocess osascript）； 返回值与现有 _focus_by_session_id 一致
G4.E1 edge unit PyObjC import OK 但 NSRunningApplication 是 None（pyobjc 极端不完整安装） focus 第一句 attr 取值失败 → catch → fallback
G4.X1 error unit PyObjC 在 fast-path 中途抛 objc.internal_error except Exception 边界吞掉 → fallback → 返回 fallback 结果

7.5 G5 ── 非 FOCUS dispatch 不受影响

ID路径等级输入预期
G5.H1 happy unit 调用 dispatch(view, Capability.RENAME, new_name=...) 路径未碰 fast-path 代码；与改动前 byte-identical 行为
G5.H2 happy unit 同上 for REVEAL_CWD / RESET_THINKING 同上
G5.E1 edge integration 批量执行 dispatcher 现有测试套件 tests/platform_/test_dispatcher.py 全部绿色，零修改

7.6 内部不变量验证（§3 I-1~I-5）

ID不变量测试等级
I-1.T1 I-1 单 worker 串行 提交 100 个 task；fake handler 内部记录"我是不是被并发调用了"（线程 id + 计数）；断言峰值并发 = 1 integration
I-2.T1 I-2 counter 单调上限 ≤ 3 fake handler 每次返回错误 5 次；检查 counter 在第 3 次后已触发 invalidate（重置 to 0） unit
I-2.T2 I-2 ok 必归零 错误 2 次 → ok → 错误 2 次：counter 序列 [1,2,0,1,2]，永不触发 invalidate unit
I-3.T1 I-3 ≤ 5 ms warm = G1.H1 unit benchmark
I-4.T1 I-4 True ⇒ 宿主前置 fake 夹具记录 frontmostApplication；focus 返回 True 后 100 ms 内观察到 host_pid 前置 integration
I-5.T1 I-5 fallback 路径不变 对比改动前后 _focus_by_session_id / _focus_by_tty / focus_host_app AST 应当字节一致（git diff 不应碰这些函数体） 静态 / CI

7.7 Mock 边界 ── 显式列表与理由

边界真实 / mock理由
NSRunningApplication unit: mock
integration: real		 unit 关心决策路径；integration 必须验证 PyObjC bridge 真的能跑通（不能用 mock 掩盖 bridge 误用）
NSAppleScript unit: mock
integration: real + fake iTerm		 同上；integration 用 fake iTerm 是因为不能在 CI 上启动真实 iTerm
iTerm 应用本身 integration: fake iTerm 夹具（一个小 AppleScriptable 进程 / 测试 stub app）
e2e: real		 fake iTerm 是一个最小的 AppleScript 字典实现，暴露 windows/tabs/sessions/id/tty 的最小子集。用 Apple osacompile 编译一个 .app 在测试 setup 中启动； 脚本 select 命令落到我们能查询的内部变量上。
QThreadPool unit: real (Qt 真实) 但 task 同步运行
integration: real		 QThreadPool 已经 thread-safe；mock 收益低
psutil unit: mock
integration: real on small test process		 避免测试依赖宿主机进程状态
logging real，caplog 捕获 测试日志级别 + 去重逻辑

7.10 Flake 预防

潜在 flake 源对策
pytest-benchmark 在 CI 高负载下偏慢使用 median 而非 mean；阈值 ±20% tolerance
e2e 真实 iTerm 启动时序不稳e2e 默认 skip on CI；本地手动跑或专用 Mac runner
fake iTerm 夹具竞态（启动慢）fixture 用 poll_until 等待 .app 完全启动再开始测试
worker 异步完成的断言统一通过 QThreadPool.waitForDone(timeout_ms=2000) 等待，不睡 sleep
