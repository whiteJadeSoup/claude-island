§4 · Error Handling

Traces to Overview · 风险 Type B（NSAppleScript 线程亲和 / iTerm AppleScript 引擎方差 / 权限吊销） + §3 不变量 I-1~I-5

错误处理总原则

  1. fast-path 失败一定有兜底。任何 PyObjC / NSAppleScript 异常路径都至少落到现有 focus_host_app， 不允许"点击后用户得到沉默"。
  2. 主线程不抛。focus() 接口返回 bool，所有异常在边界吞掉转 False + log.warning。
  3. worker 不影响 UI。worker 线程的失败仅 log，不通过任何 Signal / WorldSnapshot 反传到 UI —— 用户已经看到 iTerm 在前台，pane 错位是次要副作用。
  4. 日志降噪。重复同因失败用与 _macos_common.py 相同的"only-log-on-change"模式 （per-message 去重，避免 stderr 被刷屏）。

4.2 主线程异常吞咽边界

focus() 的实现遵守"边界全包"原则： 

def focus(self, view, *, siblings=()):
    try:
        return self._focus_fast_path(view)
    except ImportError:
        # 罕见：fast-path 内的子依赖 import 失败
        _HAS_PYOBJC = False
        return focus_host_app(view.session.pid)
    except Exception as e:
        log.warning("focus fast-path raised; falling back: %s", e)
        return focus_host_app(view.session.pid)

这里的 except Exception 是显式宽 catch —— 理由：fast-path 调用 PyObjC，错误类型可能是 objc.error / RuntimeError / Apple 异常包装等异常类， 精确枚举既冗长又易漏。统一兜底 + log.warning 比"漏一种异常类型 → 点击没反应"代价低。

worker hang 与 watchdog ── v1 明确不做

不做的理由：

  • QThreadPool 没有"杀死任意 task"的 API；要实现 watchdog 需放弃 QThreadPool，自己起 QThread + 信号量 + 计时器，整体复杂度翻倍。
  • worker hang 的可观察后果有限 —— 主线程已经 NSRunningApplication.activate 让宿主前置， 用户看到 iTerm 在前；pane 错位等同今天的 tty-miss 体验。
  • 当 backlog ≥ 10（§3.3）时已经走 reject 路径，hang 不会无限累积。

启发监控：如果生产观察到长时间 hang（如 worker thread CPU=0 但任务 30 s 未完成）， 未来可在 worker 包装一层 signal.setitimer + SIGALRM 的 timeout — 但这属于 v2 优化，不在当前范围。

4.3 日志级别约定

事件级别消息样式去重
fast-path 完整命中 DEBUG "iterm2 fast-path: host=%d, attempt=%s" 否
fallback 触发（PyObjC 缺失） INFO "iterm2 fast-path disabled (PyObjC unavailable); using subprocess" per-process 一次
fallback 触发（host_pid 解析失败） INFO "iterm2 fast-path: cannot resolve host_pid for pid=%d; fallback" 否（每次都打，量本身少）
worker pane select miss INFO "iterm2 pane select miss (id=%r, tty=%r)" 否
worker NSAppleScript 异常（counter < 3） WARNING "iterm2 pane select error errno=%d msg=%s; counter=%d" per-errno 去重 ── 同 errno 连续出现只打第一条
cache invalidate 触发 WARNING "AppleScriptCache invalidated after %d consecutive failures (handler=%s)" 否
Automation 权限被吊销 ERROR "System Events Automation permission revoked; restore via System Settings ▶ Privacy & Security ▶ Automation" per-process 一次（持久化 module-level flag）
FocusWorker reject（backlog ≥ 10） ERROR "FocusWorker rejected pane select; backlog=%d; iTerm likely hung" 窗口 60 s 一次

4.4 与 §3 状态机的对应

状态机的转移条件 ↔ 错误矩阵：

状态机转移触发的错误项
UNCOMPILED → COMPILE_FAILEDE6
READY → FAILINGE7 或 E8 首发
FAILING → READY（任一成功）—
FAILING → INVALIDATEDE7 或 E8 连续累计到 3
INVALIDATED → UNCOMPILED下一次 get_handler() 触发

注意 E10（权限吊销）会让 READY → FAILING → INVALIDATED → UNCOMPILED → COMPILE_OR_FAIL 循环每 3 次点击重置一次 —— 这是可接受的"摩擦"，因为： (a) 用户必须从系统设置恢复权限才能根治； (b) 每次循环只多花一次 ~50 ms 重编译，与已经 broken 的 fast-path 相比是噪音； (c) 我们至少在 ERROR 日志里把诊断写清楚，让用户能找到设置入口。

4.5 与现有 fallback 链的关系

关键点：fallback 链路一行不动。fast-path 是叠加在最前面的"快速命中通道"， 失败时退到现状。这是 G4（PyObjC 不可用降级）与"无新风险"的双重保证： 任何新 bug 只可能让 fast-path 退到 fallback，不会引入比当前更差的状态。
