3.1 AppleScriptCache 生命周期状态机

状态不变量下一步可能性
UNCOMPILED_*_script is None触发懒编译
READY_*_script is not None 且 counter == 0正常执行
FAILING_*_script is not None 且 0 < counter < 3下一次 ok 恢复 / 再失败累计
INVALIDATED瞬态：单一 task 帧内由 note_failure 触发 invalidate，紧接着进入 UNCOMPILED下次访问重编译
COMPILE_FAILED终态（per process）。worker 跳过该 handler 走 subprocess 兜底—

3.1.1 阈值 = 3 的取舍

候选过紧（=1）过松（=10）=3（采用）
误触发率 高 —— 一次偶发 iTerm 锁死就重编译，浪费 ~50 ms × 后续每次首调用 低 低 —— 连续 3 次失败属于"系统态确实变了"信号
恢复延迟 ≤ 1 次点击后恢复 ~10 次点击后才恢复 ~3 次点击后恢复，用户感受不到滞后
实现复杂度 无 无 同 ── 单 int 计数

计数粒度：per-handler 独立（_id_script 与 _tty_script 各持各的计数）。 理由：tty handler 失败往往来自 psutil 给的 tty 已过期，与 id handler 的脚本健康度无关； 共享计数会让两个独立健康度互相污染。

恢复：任一次成功 (execute → "ok") 立即归零。 "miss" 不算失败 —— 那是脚本健康但目标确实不在 iTerm 里（id 过期 / tty 不属于该 iTerm）； 对应路径是回退到下一 handler 或放弃，不应惩罚 cache。

3.2 Pane select 决策链

3.2.1 为什么 id miss 后还试 tty

id 是 hook 在 SessionStart 时捕获、写进 view.jump_target 的"档案值"。 它可能过期的场景：iTerm 重启、session 窗口被关、用户主动 detach 后又 attach 到新 session （iTerm 重用 id 概率极低，但 tty 的过期场景更常见）。tty 是主线程构造 task 时 通过 psutil.Process(pid).terminal() 实时取的，所以新鲜度更高。 两条线索互补 —— 一个偏稳定但可能陈旧，一个偏新鲜但可能不存在（pid 已死）。

3.2.2 为什么 miss 与 exception 走不同路径

返回归属处理
"ok"成功note_success（健康度归零）+ 立即返回
"miss"脚本健康，目标不在不动 cache 计数，进入下一条线索
抛 PyObjC 异常 / 返回 nil + errorDict脚本本身出问题note_failure（健康度恶化）+ 进入下一条线索

区分两者的目的：避免把"目标真的不存在"误判为"脚本坏了"。 前者每次冷启动 / iTerm 重启都会发生一次，是正常波动； 后者意味着脚本对象需要重建（极少见，但发生时缓存就该 invalidate）。

3.3 FocusWorker backlog 溢出策略

backlog含义策略
0 – 1 稳态（人类点击间隔 ≫ 100 ms） 正常入队
2 – 3 iTerm 偶发慢（GC / 多窗口刷新） 正常入队，DEBUG 日志
4 – 9 异常：iTerm 卡死或用户暴击点击 正常入队 + log.warning("FocusWorker backlog=%d")
≥ 10 系统抖动 / iTerm 进程僵死 reject 新提交 + log.error，调用方直接走 focus_host_app 兜底

3.3.1 为什么 reject 而不是 drop-oldest

两种策略的语义差别：

  • drop-oldest：保留最新点击，丢弃过期请求。"用户最后看见的应当是他最后点击的 pane"。
    但 Qt 的 QThreadPool 没有"从队列中取出任意 task"的 API； 实现要么是给每个 task 加 generation 序号 + run() 首行自检（额外的 main-thread 写共享变量）， 要么自己实现一个带锁的 deque + worker 线程 —— 这是大改动。
  • reject-newest（采用）：新提交被拒，前面排队的任务不变。
    天然契合 QThreadPool API：在 submit 前检查 activeThreadCount + queueLen， 超阈值直接 return False。零额外状态、零跨线程协议。

对用户的可观察影响：触发 reject 时 focus() 在主线程已经成功 NSRunningApplication.activate，所以宿主仍然到前台， 只是 pane 精度可能停留在前一次的位置 —— 与今日"iTerm 慢一拍"的体验完全一致，不构成新退化。

3.4 连续点击的 coalescing 决策 ── v1 不实现

场景不做 coalescing 的实际后果结论
用户连续点同一 view 多个 task 排队跑同一 (host_pid, id) 上的 select； AppleScript 引擎对幂等命令的处理是 O(1) 重复。 无感
用户在 view A → view B 间快速切换 A 的 task 跑完后 select A 的 pane； B 的 task 跑完后 select B 的 pane，覆盖 A。 主线程的 NSRunningApplication.activate(B) 已让 B 的宿主前置， 所以 user 最终看到的就是 B 的 pane。 无感
用户在两个 iTerm 实例之间反复切换 worker 串行执行；最后一次 task 决定终态。 无感
路径过载（backlog ≥ 10） 触发 §3.3 的 reject 策略 —— 与 coalescing 不重叠。 覆盖了

结论：v1 不做 task-level coalescing。 若 §7 的 e2e 用例或后续生产观察显示需要，可在 worker 内加一个轻量的 "latest generation per host_pid" 计数器 —— 但目前没有任何证据这是必要的。

3.5.1 PyObjC 与 host_pid 的检测时机

PyObjC import：focus() 第一次被调用时执行 try: from AppKit import NSRunningApplication， 结果缓存到模块级 _HAS_PYOBJC: bool。一次性成本 ~30 ms 出现在用户首次点击， 但此时面板已经显示完毕，用户感知不到（输入响应在 Qt 内部已 ack）； 后续每次点击是模块级布尔判断（~ns）。

host_pid 解析：优先用 view.jump_target.terminal_pid（hook 已捕获，命中率高）， 落到 _iterm_host_pid(view.session.pid) 兜底，~0.3 ms 量级，主线程可承受。

3.6 不变量小结（供 §7 测试用）

#不变量违反的可观察症状
I-1 同一时刻最多 1 个 _PaneSelectTask 在 NSAppleScript.executeAppleEvent 内 偶发 NSInternalInconsistencyException 崩溃（Apple 文档预警）
I-2 AppleScriptCache._consecutive_failures 单调上限 ≤ 3，"ok" 必归零 RAM 中数字漂移到大值；后续 task 永远在重编译路径，性能退化

I-5 所有 fallback 路径（PyObjC 缺失 / host_pid 解析失败）走的代码与当前完全一致 降级路径出现新 bug
